## 2. 4073：mode、回包和 generation

### 2.1 已证的最小语义

CP `357750..3577fa`（`cp-core.txt`）：只读取请求 `u8[msg+8]`，没有递增 generation，也没有直接调用全量 producer。

| mode / 条件 | handler 的动作 | 通知调度 `b1f9fe` |
|---|---|---|
| 1 | 立即独立回复，随后存 mode=1 | 允许 `353c18`；generation 不同才全量 |
| 2 且旧值不同 | 先存 mode=2，登记 pending | 允许 `353c18`；generation 不同才全量 |
| 2 且旧值相同 | 立即回复 | 同上，不强制全量 |
| 0 且旧值不同 | 存 mode=0，登记 pending | 不走 `353c18`，改走 `8d9ffa` |
| 0 且旧值相同 | 立即回复 | 同上 |
| 其他 u8 | 这里未拒绝；按“相同/不同”处理 | 不走 `353c18`；业务含义未验证，不应开放 |

模式值保存在 `165a720+20=165a740`。mode 1 与 2 的更完整产品命名未验证，只能按上表定义。两支都会发 d018（`ae2b76`），但它是另一路 sticky 启动通知，不是 full snapshot 触发器。

## 3. 4063 的来源、格式和副作用

**已证是 AP 的整批参数设置，不是镜头插入事件或空刷新脉冲。**

AP `3535ee4` 构造 `a04`B：先 memset 全批次，`3536840:600c8852` 取 opcode4063，`353684c:a0570179` 写外头 +2，+4 复制上层输入首 u32。`353784c` 将 `9fc`B 内体交 `36825d0`，`353786c/74` 将完整 `a04`B 交 `35358b8`，目的 `90030001`；后者以 source `80020002` 发送。不等 4063 回包，调用的 `param_5=0`，其本地返回0也不证明设备工作已完成。

```text

+8 开始：固定布局的子命令结构体，共 9fc 字节
每个子结构仍有 8B 命令头，payload 按各子命令 schema；长度并不统一。
```

完整调用点和偏移在 `cp-batch-layout.txt`，AP 组包在 `ap-batch-bytes.txt`。`35ced4` 按指定 PID 查 `10fab8c` 的20B表，再调用原 setter；不会从子包里解析任意 PID/长度。参数组涉及模式、快门、AF 区域、白平衡、增稳、曝光等，不能删成镜头所需几个 word；本次没有闭合每个 payload 的全部枚举/副作用。

**虚拟设备能否自行发4063？** 通用 dispatcher 对 source 有回调分支，并非只允许 AP，所以机械上可能分派；但没有找到一个“镜头/虚拟设备自主4063”的原发送者。找到的 CP MOVW4063 候选均是 RAM 地址低16位（例如 `1ad4063`），不能当发包证据。故“虚拟镜头自发空4063催 generation”的语义未验证，不属于本合同。替代 CP 服务可以接收原 AP 真正发来的整批设置，消费到自己持有的虚拟状态后按同一发布语义增长代数；无需写 AP 状态，也不应伪造 AP source。

### 4.3 有效、新鲜和两条通知的关系

generation 是 CP 内部u32：mutable=`165b47c`，published=`*(*(173efe8)+d5c)`，shadow=`186f4e4`。它没有被写到2040外头+4；AP `353277c..27f0` 只按2040查等待表、固定拷6d4B、兑现promise，没有在这段检查generation、长度、内嵌PID或所有有效位。**接收成功不是新鲜状态的独立证明。**

## 6. 虚拟镜头最小可行合同（草案，标明已证/假设/缺失）

### 按原消息顺序的最小集合

1. **已证**：在`90030001`接收原 AP 的`type5/4063/a04B`，source=`80020002`，消费完整固定布局到服务自己的虚拟设置/设备状态；原 AP 不等4063 reply，**不新增4063/f000**。未知子语义须保留“未实现”，不能凭命令返回0宣称已应用。
2. **已证**：在同一端点接收`type5/4073/12B`。初始化是mode1；回12B `{type1,4073,原token,f000}` 到原source。更改mode0/2需要原pending发布生命周期，若尚未实现不得先假成功。d018 是随后发往`90040193`的12B type5通知；完整CP替代服务应内部交给对应虚拟imaging状态机，不能要求或伪造一个原固件不存在的d018 ACK。
3. **已证骨架，缺状态内容**：在已消费批次、同代状态已发布、mode1/2且generation需要全量时，由source90030001分配/发送一份`type6/2040/6d4B`到80020002。严格遵守76 getter顺序、合法枚举、每块长度和设备状态一致性；这份包包含a0B的2044及20B的201b。发送成功转移消息所有权，失败释放，不能发局部栈指针。
4. **已证后续分支**：镜头状态变化可单独发`type6/2044/a0B`；光圈变化用201b等原增量通知。它们不能取代首次2040。重发mode1不能当刷新API；每一“fresh”须有模型实际状态/发布代数的依据。

### 可以提供什么，仍缺什么

- **已证/可实现**：OSAL信封、4073的token/回包格式、4063来源与固定尺寸、发布代数、2040/2044的结构、状态枚举转换、名称编码、当前光圈u16尺度。服务可以合法地拥有显式的虚拟镜头profile、光圈执行状态、可变焦距和能力；不要求读取真实机身私有setting，也不要求接物理镜头。
- **假设**：将一个虚拟镜头profile的确定值，通过已核schema发布，可驱动AP原模型；这符合设备替代方向，但本次没有执行证据。标称镜头参数只有在模型实际采用且语义已核时才能成为状态，不能为了得到UI画面填固定“成功常量”。
- **缺失/阻塞**：76块中尚未闭合的输入有效性与字段域、当前焦距/有效位到AP holder的绑定、lens ID的AP字段/编码、镜头首status产品名称与主UI显示条件、CP原API状态的最小生产入口/寿命。光圈虽有编码和copy链，实际400的生产条件未证。
- **明确不成立**：用空4063造代数；仅做d018；仅回4073/f000；用独立2044替代全量；直接写AP曝光/镜头holder；用全零扁平6d4B冒充快照。以上都不能计作“原固件认为挂了真实镜头”。

**建议下一项实现限于严格协议接入及只读采样，下一项逆向限于当前焦距/有效位与lens-ID holder闭合。当前证据足以实现/审阅通知服务骨架，不足以交付一份可宣称真实挂机的最小成功快照。**
