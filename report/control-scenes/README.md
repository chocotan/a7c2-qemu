# 原菜单控件的限定动态验收

`run-muz25xgw`使用原2.01 ALLLANG应用、显式虚拟HCI、同一新版GTK窗口和原Infra20输入链，真实鼠标/键盘逐项操作。主会话核对原LCD图与整窗截图后，另写`control-scene-proof.json`记录以下限定通过；原自动候选`gtk-input-proof.json`仍为false，不冒充完整相机已通过。

| 输入 | 实际原画面变化 |
| --- | --- |
| 前拨轮向右 | MENU 2/57→3/57 |
| 后拨轮向右 | MENU 3/57→4/57 |
| 控制轮向右 | 同页橙色选择从“动态影像设置”下移到“APS-C S35拍摄” |
| Fn | 出现原“创意外观”功能栏；MENU可返回拍摄HUD |
| 播放 | 出现原“没有影像。”；再次播放返回拍摄HUD |
| 录像档 | 原电影机图标、AF-C与0:00 HUD出现 |
| S&Q档 | 出现原“慢和快动作”模式选择说明 |
| 返回照片档 | 恢复原静态相机HUD |

![原三轮、Fn与播放的实际画面](controls.png)

这只验证本次Infra20场景和右向增量，不能推广为所有左右方向、全部页面或默认App32通道等价。录像/S&Q档的UI并不是录制产物；空卡播放也不证明JPEG解码已通过。黑色取景区及空曝光栏仍表明CMOS/镜头/曝光/编码链未完成。

MODE八档的请求/原枚举/单次status已有静态及host测试，但本轮所存P/A/S/M/AUTO画面各有一拍延后：例如请求A的采图显示P，请求S显示A。可能涉及原模式说明与异步绘图，尚未定因；没有擅自调整原始编码或标为模式全通过。后续需确认稳定帧或原状态读回。

后续`run-7_efjv_8`实际读原Getter的dial值0/1/2/3/4、switch0，且原32B收到的位置值正确；4秒稳定帧仍旧档。这只证输入档位，不等于用于图标的曝光模式状态同步。`run-5e2c8yym`原1003提交ID与当时on描述符相同，不支持仅凭名字切换off；`run-9ecqemfc`在1005时按原锁/引用租约重读同bitmap，已记录样本均与保留像素摘要一致。两项是排除边界，不是证明整条绘图链正确；正常显示、缓冲选择和完成通知均未因假说修改。下一点是原`translator_icon_exposure_mode`实际读取的model字段。

原稿中的短按测试超时、私有DISPLAY漏传、共享PPM被改写等失败记录全部保留。当前测试的键盘调用统一走私有Xvfb，采图从VM已验证PNG按序号保存不可变副本，再核RGB SHA；不能用发送返回0或hash不同代替本次人工内容审查。
