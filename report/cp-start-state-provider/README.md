# CP start-state provider: explicit public property repository

The new C provider binds one real input: the complete 256-byte `01250006` property from an explicitly selected, authenticated public BK4 repository. The currently used primary bank has no such property and returns `-ENODATA` without changing input masks. A separately selected secondary virtual repository can supply profile byte 0 from its actual payload. There is **no automatic fallback**, and this does not establish native CP's repository selection, runtime consumption, LIF initialization or camera readiness. The existing data owner still refuses the 16-byte 3003 reply with the remaining inputs absent.

Later integration keeps these APIs unchanged and adds a separate [CP initial-stage owner](../cp-property-repository-contract/README.md). Its CP_PRIMARY is the original constructor's supplied04000000 repository, explicitly populated from the authenticated public CP Backup initial stage; it does not rename this file-offset-zero PRIMARY policy. It delivers the owned profile through the existing callback API and separately records mode=1/profile=0. Frozen-stage checksum mismatch is refused. The actual stage/parameter-copy/runtime helper is documented in [the combined input stage](../2026-10-27-unified-camera/cp-owned-input-stage.md); native boot/alias and remaining status inputs are still unproved.

This is a bounded contribution to the parent's unified development batch. Authorization is the delegated offline owner-authorized public-firmware implementation task. Only this new report directory, `cp-start-state-provider.{c,h}`, `test-cp-start-state-provider.c` and `test_cp_start_state_provider.py` are owned here. Existing changes, status algorithms, 42 existing source pins and copy-out logic are preserved. No VM/system QEMU, network, private/full-system assets, camera or physical SD was used. This section is the scope record; report flavor is ordinary firmware reverse analysis (`null`).

## Reproduce and integrate

From `2026-10-17-qemu-native-camera`:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m pytest -p no:cacheprovider runtime/analysis/test_cp_start_state_provider.py -q
python3 report/cp-start-state-provider/load_public.py --policy primary
python3 report/cp-start-state-provider/load_public.py --policy public-secondary-virtual-property-v1
```

Observed result: **6 passed**. The tests compile C11 with `-Wall -Wextra -Werror -pedantic`, once normally and once with ASan/UBSan. They verify 256 profile values, complete payload readback, checksum/table/size failures, unknown and invalid masks, unsupported property IDs, overlap, stale/torn guards, process/origin protection, unchanged state/output on error and blocked replies. They also run both actual public banks through C, compare all 256 secondary payload bytes against SHA-256, authenticate the original CP and seed, verify nine new backend windows and reconstruct all 190 same-run 4063 slots. Public-asset and local-run checks skip only when those inputs are absent. Host C tests require no firmware.

The API is [cp-start-state-provider.h](../../runtime/analysis/device-models/cp-start-state-provider.h); the source is [cp-start-state-provider.c](../../runtime/analysis/device-models/cp-start-state-provider.c). Link the provider with the existing `cp-start-state-data.c`. No build/runtime file has been edited by this worker.

1. Authenticate public assets with `load_public_bank(base, policy)`. Its policy argument is mandatory. It verifies full CP, full ALLLANG seed and exact selected-bank SHA-256 before returning bytes. The C parser checks BK4 checksum/structure; the caller must supply the loader's authenticated immutable bytes, since an additive checksum is not an identity check.
2. Initialize a caller-owned provider with `cp_start_state_provider_init`; every input/result bit is unknown.
3. Hold the same source lock as the existing data owner and call `cp_start_state_provider_bootstrap_property` with an explicit `CP_START_STATE_REPOSITORY_PRIMARY` or `CP_START_STATE_REPOSITORY_SECONDARY_VIRTUAL`. The repository enum must match the authenticated loader choice. There is no retry against another bank inside this API.
4. The primary returns `-ENODATA`, preserving the entire provider. The explicitly selected secondary copies its actual complete payload, records `prefetch_result=256` and the selected repository, and passes the real context to the existing property's consumer. Only profile's predicate-known bit is added. This is a new virtual-owner policy, **not a change to the existing primary-only CP3006 loader or the original borrowed backup window**.
5. A genuine later property callback can call `cp_start_state_provider_deliver_property` with full `01250006`, exactly 256 bytes and 256 known mask bytes. Partial/unknown data is rejected atomically. Callback-only delivery carries no bank claim (`repository=0`). After a bootstrap, the repository records the bootstrap source; `property_delivered` separately records a later callback, which need not come from the same repository.
6. Supply other actual events to `provider.data` using the existing owner's API. Read `cp_start_state_provider_snapshot` under the current coherent guard. HOST_TEST remains HOST_TEST; the provider does not relabel it VIRTUAL_SOURCE. Source checks are caller contracts and do not prove native execution.

The readback retains the entire property context, repository enum and separate bootstrap/delivery flags. `property_bootstrapped` means this virtual owner consumed the selected bank; it does not mean CP natively prefetched it. A snapshot does not call the fourth getter. The provider performs no send, reply authorization, lease, generation advance, publication or AP application.
