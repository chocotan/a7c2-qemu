# 原固件触屏输入

独立 A7C2 QEMU 产品现可在 LCD 区域用鼠标左键模拟单指按下、拖动和松开，原 AP 实际消费坐标并刷新原菜单。宿主 GDK 单指触摸共用同一路径；物理触屏设备未参与验收，多指手势未实现。耗时优化按用户要求暂缓，沿用当前结果。

## 使用

按现有产品启动方式打开相机窗口，待 LCD 显示相机画面后，在画面内按住鼠标左键即可触摸，移动鼠标可拖动，松开结束；黑边不产生新触点。失焦、取消或关闭窗口会尝试释放触点。触屏设置、可触摸区域和页面行为仍由原固件控制；原固件忽略触摸的区域不会改发方向键。

原菜单点击前后：[原图](menu-before-touch.png) → [触摸响应](menu-after-touch.png)，完整机器收据见 [validation.json](validation.json)。

## 范围

- 前端复用 `runtime/analysis/camera_ui.py` 的原 LCD，按实际等比缩放映射 640×480 坐标，黑边不产生新触点。
- 传输复用已有串口 owner 和原 App32 输入服务，不额外创建 guest 输入进程。
- 触点需要完整的开始、移动、结束和取消生命周期。失败保留 owner 与不确定状态，关闭和失焦沿原通道释放。
- 使用独立本机实例；不控制用户已有窗口，不连接真实相机或真实 SD。
- 触摸是否在当前页面生效由原固件设置与消费者决定，不用坐标命中后代发方向键来替代触屏。

## 原事件 ABI

原 `appFw.so` SHA256 为 `2ea02f7ecbc5bb917316fe8ef4ce5ffd87eb66efaae78ba2ce11420552df539b`。主会话直接复核产品 ELF 和研究 ELF 的完整摘要及以下指令：

- `0x179a0d0` 取 word0，`0x179a0d4` 比较 `0x270`；消息沿原 `0x5503e0` 队列传递，长度 32B。
- `0x179a1e0` 取 word1 的低 16 位到第三参数 y；`0x179a1e4` 取高 16 位到第二参数 x。因此 `word1 = (x << 16) | y`，面板全屏范围 0..639、0..479。
- word2 为 phase：1=PRESS，2=MOVE，0=RELEASE。word4 低四位为 finger，首版固定 0；word6 保持原 App 输入的 from_type=0；其它 word 保持零。
- PRESS `0x1797484`、MOVE `0x17977f4`、RELEASE `0x1797908` 最终调用原 WidgetSystem 的鼠标事件入口。MOVE 每六条才转发一次；RELEASE 使用该触点槽内最后坐标。

这些字段可由现有五个 body 参数承载，故 `inject-key.c` 和常驻串口协议无需修改。原 App 的触摸禁用/区域/方向门卫继续执行，消息被原 App 接收不等于当前页面会响应。

私有源证据：`analysis/scratch/product-touch-20261111/abi/`。原固件、原语料和运行日志不进入公开代码包。

## Host 验收与边界

集中验收使用两个 worker。输入组 198 项、5 子测试通过；GUI 组中未变的 65 项、6 子测试通过，新增触屏夹具的黑边方向和 GTK3 恢复 API 修正后，全部 67 项覆盖通过。另补两项实际 X11 拖出画面释放、独立半按快门保留测试，以及 6 项冷启动入口回归。合计 273 个不同测试、11 子测试；旧失败 stdout 保留，不回填。

测试实际执行原 C 注入器并比较 32B 消息，也使用生产 `PersistentAppInput` 完成 PRESS/MOVE/RELEASE 和正常 STOP。GTK 鼠标测试由专用 Xvfb 中的 X11 事件驱动，手指序列测试直接调用已连接的 GDK 回调并提供不同合成序列。后者不能提升为物理触屏设备已验收。

首次原 AP 验收在启动前被 loader 拒绝：新复制试验盘仍有 WBI2 标记，会选择 mode11；冷启动 builder 要求 mode1。原失败保留，未启动 VM。仅在独立试验盘备份并清除缓存标记后，按原 loader 选择冷启动继续；这不改变产品 loader，也不是 WBI 恢复验证。

第二轮发现既有启动器将高位 DRAM `loader_args` 配好却漏传给 QEMU，串口保持零字节。仅补回最终命令的数组传参，WBI 分支已将该数组置空，保留它原有行为。该轮经专属 LCD QMP 正常退出并确认 owner 消失，未发送触摸。另有 6 项冷启动入口回归通过；后续真实 guest 已验证装载。

## 原 AP 实际验收

独立 `run-0lq8gtyq` 在原拍摄界面进入 MENU 后，由 X11 鼠标真实点击 LCD 的 `(24,164)`。原 App 队列接收到 `[0x270,0x1800a4,1,0,0,0,0,0]` 和对应 RELEASE，原 LCD 布局及焦点像素改变。随后真实拖动收到 PRESS、8条MOVE、RELEASE，再按下并执行取消收到 RELEASE，均未遗留触点。

本轮源码前后摘要一致，更新后的虚拟 SD 保存通过，19卷冻结完成，QMP quit确认、owner返回0、无VM信号、进程组消失且租约重新获取通过。该证明是原 App 输入及菜单响应，不扩大为 CMOS/AF/拍摄成片、物理触摸控制器或完整硬件启动链已完成。

原始失败保留：v1 WBI冷启动前置拒绝；v2 loader参数遗漏、零串口；v3验收回调签名不匹配；v4既有教学返回HUD变体未被验收器识别。v3/v4均正常保存退出；v2由专属LCD QMP正常退出，原失败状态不改写。

固件异常或串口边界不确定时，松开可能失败；保留 owner 和不确定状态、阻止保存或关闭宣称成功，遵循既有机身输入策略。
