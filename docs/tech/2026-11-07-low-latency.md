# 连续 LCD 与原 App32 输入

本次修改直接维护在本产品的 `runtime/analysis/`。运行所需内容输入仍为用户的 ILCE-7CM2 2.01 ALLLANG `BODYDATA.DAT` 与固定 QEMU 源码；没有研究仓库、整机 dump 或历史实验目录的运行依赖。

最新产品实跑 `run-u9x23cjn` 的 12 个真实窗口样本中位数为 **97.3ms**，最大值 **121.1ms**。连续显示与原输入闭环已实际工作，但“所有样本都小于 100ms”仍为 false。该轮使用默认输入/显示配置、显式 `virtual-rom-v1`，未额外启用输入路由或启动深度 trace；默认原 App32 消费记录仍保留。不能用中位数掩盖尾部，也不能只据采样配置宣称原创 120fps。

## 显示

原 AP 提交的 HOSDAP02 完整帧继续经过容器格式、长度、序号、物理范围和摘要检查，再由 guest `ramfb-viewer` 转为 QEMU ramfb。RGBA4444 转换使用 65536 项查表，每个输入值均与原公式逐值对照。容器摘要中第 40–47 字节的归零规则保持；摘要循环展开只减少循环开销，独立旧公式验证小长度边界和整个帧。

独立 `lcd-qmp.sock` 连接从本窗口 owner 的 QEMU 子进程读取原 ramfb。连接校验 socket 所有者、`SO_PEERCRED` 和进程祖先关系；图片必须为完整的 640×480 PPM。GTK 接收经内容校验的 PNG，连续显示时停止自动排队串口快照，手动“刷新 LCD”仍可做原诊断。

guest 扫描周期为 10ms，QMP 采样目标为 120 次/秒，GTK 状态周期为 16ms；新原帧到达会直接排入 GTK 主循环，不必等待下一次状态 tick。这些配置值不等于已测得的原创画面变化帧率。消费者分别记录成功读取次数与像素改变次数，静态页的重复内容不会冒充新画面或成片。

## 输入

`inject-key.c` 的原单次 CLI 与常驻模式共用原 osal 分配、App32 的 32 字节布局、原发送接口及发送失败后的释放处理。常驻模式在窗口报告运行中之前取得真实 ready，未发送预热键。

输入期间，同一串口 owner 将递增序号及五个原字段直接交给常驻发送器，必须收到相同序号和原返回码 0 才向 `InputSession` 返回完成字节。需要诊断、快照或保存时，先发送递增的 `STOP`，取得本次独有的 shell 返回码标记，再交回原 shell。序号不匹配、超时或写入边界不明会保留不确定状态，禁止重试另一通道。

原 `InputSession` 的持有、共享快门、释放顺序和错误清理继续生效。tap 明确保留至少 50ms，性能优化没有缩短按压时间。原消息成功发送与原 AP 实际消费分别取证；消息回执不证明拍摄或录制完成。深度输入路由和启动 trace 属于额外诊断，其开关、观察器以及每轮全部样本分别留档，跨轮数值不当作单因素性能对照。

## 关闭

原 capture 关闭门、原 Fsys Flush、整卡读回和设置发布仍决定是否可以关闭。保存拒绝或失败时保持 VM 与 LCD；最终收尾先停止独立 LCD 消费者，再关闭控制 socket，让 launcher 正常发送 QMP quit。自然启动 owner 只等待退出，超时保留 owner 与租约，不发送 TERM/KILL。

每轮正常 QMP 收尾生成 `qmp-quit.json`，分别记录尝试、原 QMP 确认、实际返回码和信号列表。窗口消失或进程消失本身不算正常退出证据。

## 验证入口

```bash
python3 -B tools/test-low-latency.py
```

该入口以八组并发运行，使用独立临时目录、日志和 JUnit。覆盖真实管道回执和交还 shell、坏序号超时锁定、原 App32 ABI 的 ASan/UBSan 检查、输入持有/释放、GTK、正常 owner 收尾、65536 种像素转换、完整帧读回错误保留、旧摘要参考、原 glibc 交叉构建与既有 HCI 模型。

真实窗口测量工具为 `tools/measure-startup-navigation.py`，仅供专属 1360×930 的 X11 测试窗口使用。它等待原语言列表实际出现，由独立 xdotool 脚本执行真实的 50ms 按下/释放，截图循环不会延后松键。它直接读取窗口中的 LCD 区域，检查原焦点文字的像素变化，分别记录首可见时间及第二次稳定确认时间。直接区域读取已与旧的全桌面截图裁剪逐字节对照一致。测试窗口及原始输出均留在被忽略的本机诊断目录，不纳入公开代码包。

历史产品样本保留：早期连续显示版本的窗口中位数约 178ms；常驻 FIFO 约 145ms；短 shell 命令与首次前台版本约 130ms。它们均未达到 100ms，不会被替换为后来版本的结果。研究路线此前的 17.575fps / 100ms 内结果也不作为本产品通过证据。随后原帧事件直达 GTK 的 60 次/秒采样版本取得 95.0ms 中位数、101.5ms 最大值，严格 100ms 仍有一笔未通过；原始 12 个样本完整保留。最终版本的实测与退出范围以本次公开验证收据为准。

## 原启动错误的范围

`A7C2_VIRTUAL_HCI=virtual-rom-v1` 使用本产品已有的有限虚拟 HCI 与原 BSA 管理状态机。它属于显式选择的虚拟功能配置，不代表真实无线、手机配对或完整蓝牙。原“系统出错”页面没有被修改或屏蔽。

同一 `run-u9x23cjn` 已通过原按键逐页进入拍摄 HUD；本轮原 `CreateScreen(0)` 控件数为 565，原窗口实图已人工审阅，未见 `0x30c` 系统错误页。现有首设自动检查器仍因固定历史页序列要求而失败：这次没有出现它要求的 `0x1e6` 教程页。原失败文件保留，人工 HUD 可见不替代该检查器通过，也不证明完整首设状态持久化。

后续原日志出现 `model::set_pre_power_off_seq`，原 screen `0x309` 与黑帧实际出现，MENU 未恢复原菜单。本轮关闭了深度启动 trace，未捕获电源因子；历史相似故障另有 APO1 factor8 证据，这一轮不独立提升 APO 归因为已证实。完整唤醒、长期运行与本轮 MENU 验收仍为 false。

正常关闭已完成原 Fsys Flush、32×4MiB 跨通道 FNV 一致、整卡 SHA256 读回和 fsck0；原 QMP quit 确认、owner 返回码 0、无信号退出与用户原配置未变均已核对。消费者实际读到 43,155 个有效原 LCD 帧，耗时 359.892 秒，即 119.91 次/秒；其中 119 次像素内容改变。该读取率不是原创画面变化帧率，也不算取景或成片。

USB 认证、P1 安装、完整硬件启动和拍摄成片不由本次显示/输入改动提升为通过。
