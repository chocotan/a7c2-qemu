# 大步骤 4：把输入送到原消费者，再看业务效果

这篇解决键码、事件类型和输入故障定位，不把半按、REC 消费或模式图标变化当成 AF/拍摄完成。

变量见[索引](README.md)；原输入运行证据来自报告，本次没有发按键。

## 小步骤 1：从已知导航键校准映射方向

**问题 →** 原始键值、UIBIZ 逻辑枚举与业务事件不是同一套编号。
**现象 →** 旧 MENU `0x14000102` 进了其他映射，主循环收到却不打开预期菜单。
**误判 →** 从动作表抄 REC `0x1c`，直接作为 App32 原始键发送。
**定位 →** 从原 App 队列复制、`0x17951c0` 哈希重映射，再追到动作表。
用已经真实验证的导航键反校方向：`3→2`、`30→6`、`1ab→13` 等。
**解决 →** 将原始 App32、canonical UIBIZ 和下游事件分别建表。
原表有 1120 对，但只有 1117 个唯一 raw；插入逻辑保留首项。
例如 `a7→f/10` 的重复键不能用普通 dict 保留末项，否则全按会错解。
**剩余 →** 静态映射只证明编码关系，按键角色和业务仍须现场验证。

## 小步骤 2：区分两条输入前端

**问题 →** 直接 App32 输入和 Infra20 输入经过的原逻辑不同。
**现象 →** 方向导航能用，但原缓存、repeat 或唤醒行为不一定相同。
**误判 →** 两条通道末端都进 app，就认为完全等效。
**定位 →** 原 `libObj` 的 Infra 回调链更新键缓存，再转到 appFw 队列。
Infra20 `0x807a0020` 布局为 `{key,sub,status,ex,from}`。
已核读取前 16B，后续强制 from=1，第五 word 不决定最终 from。
**解决 →** 对照时记录输入通道和真实原消息，不把前端选择藏在测试驱动里。
**剩余 →** App32 绕过部分缓存/repeat，不能拿其成功证明物理键/省电唤醒完成。

## 小步骤 3：按事件类型选择正确序列

**问题 →** 所有控件都发 1/0，会把拨轮和位置事件弄坏。
**现象 →** 一次方向跨多项、模式断言、拨轮出现多余动作。
**误判 →** 长按一秒也叫单击；拨盘正增量后一定补零释放。
**定位 →** 按原输入结构区分短按、signed increment 和 position。

| 已验基础例子 | 原始码 | 序列与范围 |
| --- | --- | --- |
| 上/下 | `0x3/0x30` | guest 50ms 短按：1→0 |
| 确认/MENU | `0x1ac/0x1ab` | 1→0；指定菜单导航 |
| 删除/C2 | `0x1f8` | 1→0；验过帮助页，非照片删除 |
| 右后拨盘 | `0x10000013` | 单发 `-1024/+1024`，不补释放 |
| 模式位置 | 依原 MODE 转换表 | 单次合法 status，不套普通键序列 |

**解决 →** GTK/QEMU 输入抑制 held repeat，暂停/断线拒绝新输入，点击后恢复焦点。
模式使用标签→已核位置值；未知标签和普通 scalar MODE 被拒绝。
**剩余 →** 这些例子不能推广为所有页面、全部自定义键或三轮业务全通过。

## 小步骤 4：把枚举标签与真正原模型对上

**问题 →** 名字数组顺序未必就是枚举数值起点。
**现象 →** 原菜单与 HUD 看到的模式不符合前端标签。
**误判 →** 只因数组顺序 P/A/S/M/AUTO，就按 0 起始发送。
**定位 →** 核显式 ID `0x1c75`：AUTO0/P1/A2/S3/M4，再核原转换器。
原转换路径的 status 与模型值还隔一层，不能对整个表粗暴 +1。
**解决 →** 前端修正 AUTO1/P3/A5/S4/M6 的 status，逐张原 LCD 验 P/A/S/M/AUTO。
MR 与三档开关的限定 HUD 证据分别记账，不混成完整参数回载。
**剩余 →** 模式标识变化不证明真实曝光；remote/PTP 属性也不是 HUD 当前帧的直接证据。

## 小步骤 5：确定键断言要查业务数据，不先怪按键

**问题 →** 日期设置按确定后进入异常监视器。
**现象 →** `get_date_time_by_changing_current_area` 在 `appFw+0x2524f98` 触发断言。
**误判 →** 确定键协议整体错了，或只要 insmod udate 就修好。
**定位 →** 重放原操作，记录请求 `0x0090013d` 的 transport、status、日期和 flags。
仅加载 udate 的阴性对照仍失败；命令2返回零日期/flags3，命令3有默认合法日期。
**解决 →** 用原 udate 服务，在已核未初始化状态下走原 BY_BOOT=4 初始化。
取原固件默认 `2023-01-01`，读回合法日期并检查时间推进；失败阻止 app 启动。
原 123 步重放通过，未删除 assert、未改 app 日期模型或注入假成功。
**剩余 →** 未证明所有时区/夏令时、编辑保存到 RTC/FEC 或跨 VM 时钟持久化。

## 小步骤 6：异常后停止积压输入

**问题 →** 原异常发生后，host 还继续收键。
**现象 →** 后续只看见“已发送，未确认画面变化”及“队列已满”。
**误判 →** 把队列满当第一原因，重复点击掩盖原断言。
**定位 →** 完整 console 做跨 chunk 增量监视，而不只检查单条命令输出。
**解决 →** `FirmwareMonitor` 检测 `Entering exception monitor.` / `Exception>`，
立即失败、停收输入、清 pending，保留异常前后的原始记录。
**剩余 →** 监视器改善可见性，不救活已经 abort 的 guest。

```bash
# 执行目录：$PKG；只读定位前端、原消息与异常监视实现
cd "$PKG"
rg -n 'FirmwareMonitor|Exception>|pending' runtime/analysis/menu_live.py
rg -n '807a0020|app|status' runtime/analysis/inject-key.c
```

## 解决了什么，仍未解决什么

基础导航、指定拨轮/档位和部分机身控件已有原输入/LCD限定证据。
后来 C1、半按、全按、REC 的 1/0 被原 App 消费，不等于各自拍摄功能通过。
半按回 HUD 不能叫合焦；AF-S 图标不能叫 AF 完成。
接下来要沿 lens/AF/AE、帧与编码继续追，而不是在输入端补 ready。
