# 普通 AP USB 功能选择与 MSC：实际边界（2026-11-10）

## 结论

本轮已恢复到原 AP 的 USB 初始化、真实功能选择页和“正在连接至海量存储器…”原 LCD。**宿主枚举、MSC function 绑定、原 MSC DSO 消费和宿主块设备读回均未通过**；`ordinary_ap_usb_menu_route_verified=false`、`msc_storage_readback_verified=false`。

公开失败边界收据：`validation/usb-msc-frontier-20261110.json`，SHA-256 `a09408482e8c0dd34ab6fc4b61d7530955a59befb48560a71ecd5f14cf55ae5b`。它不把多轮局部进展拼成成功。

## 实际证明的链路

显式 `virtual-functional-sony-usb-device-v1` 与 `A7C2_USB_MSC=1` 下：

1. 原 `insmod_drv2` 的 `usb_portMonitor → usbg_sen → usb_extcmd` 均实际加载。`usb_extcmd.ko` 仅在显式 USB profile 按原 SHA `63554be9f7bf7cbba3d9de16ce3d8675e3b60a323be1fa92839fa9eec0caa8c2` 准入；其它未建模模块仍拒绝。
2. MSC IMDB 只恢复原 `libInfraUsbCmn.so` 与 `libUsbControl.so` 初始化。实际日志出现 `UsbControl_Init → usbif_initialize → openSvc`，openSvc 从 state1 到 state5、rc0，并打开原 event/otgcore/usbcore 设备。
3. VBUS 后出现原 `0x25b` 功能选择页。默认第0行是 USB 流式传输，MSC 是第1行；原 DOWN 的 press/release 与 LCD 行变化均核齐后才 ENTER。
4. ENTER 后再次实际 snapshot/display，得到“正在连接至海量存储器…”帧；fusb 内部 VBUS latch 和读回均为1。
5. 最新被动资源观测只看到原 `SVC_NOTIFY event=1`；没有原模块装载、storage create、`libInfraMscServer.so` 加载或可用 EP0 描述符。宿主控制面仍为 `gadget_not_ready`，未读取任何宿主机块设备。

## 关键根因

### IMDB bind 存在不等于实际消费

`bootin.sh` 使用 `LD_LIBRARY_PATH=/simulation:/usr/lib:/lib`。最初 MSC 候选只 bind 到 `/usr/lib/libIMDB.so`，但 `/simulation/libIMDB.so` 的默认副本优先被 im.elf 加载，mountinfo 因而造成过误导性表象。

修复后，`original_cold_boot.usb_imdb()` 将同一通过身份校验的候选同时映射为 `libIMDB-msc.so` 和实际优先命中的 `libIMDB.so`。默认 profile 不产生这些文件；host 测试核两名称指向同一候选及默认关闭。v13 的原始 UsbControl/openSvc 日志证明这些服务被初始化。

v26 的 `build/payload/libIMDB.so` 当前仍是默认副本，而 `libIMDB-msc.so` 是 MSC 副本；不能把该同名磁盘副本直接当作 guest 加载内容。当前构建代码将两个 guest helper 名称映射到后者，v26 保留的 helper 清单也对两名记录 MSC 摘要，启动日志有两条 `COLD_COPY ... verified=1`。这说明当时复制环节按 MSC 摘要验收；现有证据仍没有同代进程实际加载映射的完整摘要，不能仅凭路径或初始化日志证明最终动态加载身份，也不能改写旧收据。

### 不再使用固定语言方向或旧帧

验收驱动曾错误假设所有起始语言都能用“阿拉伯语起向下两次”的 helper。实际运行还出现日语、越南语等起始页。最终逐键读取当前可见目标/选中行，每次要求原输入边和 LCD 实际变化；目标不可见时才滚动。阿拉伯语右对齐标题另有独立、screen0x12d 绑定的内容分类与自包含位图回归。

MSC ENTER 后必须重新 snapshot/display；旧选择页截图不能代表后来的连接状态。

### 共享快照故障已单独修复

持久 `/tmp` 的固定 `.part` 在失败/冷启动后可导致 `open EEXIST`。`hosd_persist()` 改用 PID+原子 ticket 的唯一临时 inode，撞名跳过而不删除旧证据；写后全文 pread 和原子 rename 不变。该修复已在含旧 `.part` 的故障盘上实际恢复启动。

## UI→MSC 提交链闭合（静态）

基于与 v26 同身份 `appFw.so`（SHA `2ea02f7e…df539b`）的原指令与重定位，UI 到原 MSC 入口的完整调用链已闭合：ENTER 处理只保存选择值并打开 `25c` 连接页；连接页初始化 `0x207665c` 根据网络/FTP 配置设置等待标志（`self+0x303/+304/+305`），需完成事件 `0x01000053–0x01000058`、`0x01000116`、`0x01000289/0x01000291` 推进后才进入 MSC 请求提交 `0x24f2db4`；该提交受全局 gate（`B+0x7e4e608`）限制。请求 id `0x367` 经 `0x24871a4` 分派、`0x328eef0` 创建 sequence、`0x3222ad0` 入**调度组 6**（表 `0x4c02e64` 处值为 6），最终才到达原 run `0x34796b0`。

因此 v26 显示连接页不证明 MSC sequence 已提交；组 0 的历史采样不能回答组 6 队列状态，当前也不能把缺失的 `UsbBusPower` 或历史 EE20a3 判为本次根因。下一轮受控运行应在 `0x207665c`（X0=self）、`0x19005f4`（X0=self,X1=ds_event*,W2=事件ID）、`0x24f2db4`（X0=输入,W1=flag,X2=assoc,void返回）、`0x24871a4`（X0=request,void返回）四处加被动 entry/return 观测，并采样组 6 header/pending/active。`0x20761ac` 开头为 CBZ/CBNZ 且 corpus 尺寸记录错误，不可用通用 trampoline。

## 仍未完成

`A7C2_USB_GENERATION_OBSERVE=virtual-usb-generation-observe-v1` 是默认关闭的虚拟诊断，仅在原 cold USB profile 和 `guest_errors` 日志启用时向 QEMU 传入固定的 `generation-observe` 属性。两线程宿主合批两组分别 36、34 项通过，产品两个接线文件与已测候选完整 SHA 一致；真实 QEMU 属性消费及 MSC 枚举均未验证。原始批次见 `scratch/owner-media-usb-batch-tests/run-sc2e9dl0/`。现存 USB 构建收据绑定的 DWC3 源码已与当前源码不一致，入口会拒绝；需要新构建。当前构建脚本自带的旧 QEMU 烟测在失败时可能发送终止信号，须先完成安全 owner 收尾，不能直接执行该重建。

历史 sender 调查将 group0 停在原 `20a3` EE-capability 通知 future 等待，但**当前 MSC 与该等待的因果同一性尚未证明**。研究线 host 全验证的 EE NormalWake cold 服务已作为显式 opt-in profile 接入产品 observer 构建链：`A7C2_USB_EE_NORMAL_COLD=1` 且显式传入**树外**私有 prepared header 时，`sony_usb_device.py` 才把 `ee-normal-wake-cold.c`／`ee-capability-input.c` 与 `usb-ee-normal-cold.inc`（已复制进产品 `source/usb-device/`，来源与原 SHA 记入 `SOURCE-ORIGINS.json` 新条目，仅 `ee-normal-wake-cold.h` 声明了一条 include 重定向适配）链入原 AArch64 observer DSO；默认构建不定义该宏、不链接任何 EE 代码；构建链接输入改为经原 initramfs 完整摘要校验的私有库副本。私有输入只接受外部路径：公开树内路径、symlink、缺 profile、非 `1` 值或合同 marker 不符均在编译前拒绝。

该接线目前**仅 host 可验证**：`test_usb_ee_normal_cold.py` 覆盖构建、默认 off 时产物无 EE 符号/文案、profile 门控 fail-closed、clang AArch64 互斥语法检查与 SOURCE-ORIGINS 血统复核，全部使用显式标注的合成 fixture。**原 AP 实际消费仍未验证**：该 profile 未在产品 VM 运行过；研究侧 v4–v8 实际运行中 `FUNCTIONAL_INIT` 未出现、目标 `0x80020002` queue 注册未观察到，20a3 等待与 MSC 请求的因果同一性仍未证明。启用该 profile 需设备所有者用真实完整 Backup 生成私有输入（`prepare-ee-normal-wake-cold.py`），host fixture 不代表原消费者登记。下一步仍应恢复/观察原通知生产者与 MSC 请求的真实提交链，不能手写20a3、清 inhibit、直接调用 START 或伪造 function/宿主枚举；研究侧实际边界见 `final/a7c2-re/report/2026-10-17-qemu-full-system/USB-EE-NORMAL-COLD.md`。

当前工作区补上了 `tools/run-original-cold.py --usb-msc` 对这对显式 EE 变量的传递，缺一或 profile 非 `1` 均拒绝；私有头要求树外、非 host 临时路径、可信祖先、单链接且 `0600`，构建前后核对文件身份和完整摘要，编译器只读取校验后封存的匿名内存副本。冷启动 audit 与 USB observer 的链接输入来自同一套与受保护 `menu-initramfs.cpio` 四个成员全 SHA 绑定的 `0600` 私有副本，再复制为封存的匿名描述符交给编译器；原库权限不变。live 输出位于 `runtime/analysis` 时，私有副本保存在独立的 `runtime/observer-private-inputs/`，并记录路径及收据。**源码及 host 构建已通过本轮集中回归，原 AP 实际验证仍未执行**：见 [非 CP host 验证摘要](../../validation/non-cp-host-20261115.json)，USB/冷启动组 31 项通过、0 跳过；私有原始收据位于 `scratch/non-cp-mainline-tests/run-ty7ejjns/`，绑定源码、原库、基准 initramfs 及编译工具前后摘要，结果 SHA-256 为 `13f8be6ca3061fc23df4ae228067443aa0d8b9ecc823f536590f750cc6b30508`。这组还执行了读取八个研究来源文件的历史血统测试；八项在测试时匹配固定摘要，主会话随后再次完整读回一致，但未分别采集其测试前摘要。编译工具的目标文件前后摘要一致，入口路径为测试后再次核对；独立限制和零 skip 逐节点复核见 `scratch/non-cp-mainline-tests/run-ty7ejjns/review-addendum-v1.json`。后续又把 audit、observer 和 readelf 的临时目录固定到已打开的项目内私有目录 FD；[两线程 host 复验](../../validation/non-cp-private-temp-host-20261115.json) 两组共 30 项通过、0 跳过，含真实交叉编译及目录替换模拟。后续共享串口和 owner 收尾另有源码修正：输出超限不截断原日志、未知边界禁止后续串口及 QMP quit、无信号保留 owner；这些更改已纳入后续两线程 host 批次 `scratch/non-cp-mainline-tests/run-c4l77_rs/`（409、426 项），但真实单 AP 验证仍未执行，不能由 host 结果提升。
