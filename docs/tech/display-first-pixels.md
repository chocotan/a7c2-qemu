# 大步骤 3：从黑屏到第一份可信原厂界面

这篇解决 AP 软件 OSD 的像素生成、提交和显示，不解决 CMOS 取景、完整 CP 合成或实体面板等价性。

变量见[索引](README.md)；历史动态结论引自原报告，本次没有运行显示链。

## 小步骤 1：先给黑屏分类

**问题 →** 内核没起、没建屏、只清屏、没提交和显示桥没接，都可能看起来一样。
**现象 →** 原 `0x308/count28` 启动控件存在，GPE 却只清空位图。
**误判 →** “屏对象已建立”就说菜单已画好；或无画面就回头改内核。
**定位 →** 分别记录 app 生命周期、屏 ID、notifyDraw、drawFramebuffer 和输出消费者。
**解决 →** 历史受控菜单用原九参数生命周期入口 `0x1e78870`，
经菜单 controller `0x346` 自然创建 `0x2ca/count44`，保留原析构、构造和请求泵。
**剩余 →** 这是早期定位显示的受控入口，不能当自然冷启动已恢复。
后来的自然首设/HUD验收另看本包 validation，不能混用两条证据。

## 小步骤 2：先把像素格式和字节序搞对

**问题 →** 请求确实来了，画面却只有清屏、错误颜色或无法辨认的字形。
**现象 →** BitBlit 曾产生 69 条不支持请求；callback 偏移也曾套错。
**误判 →** Fill 与 BitBlit 共用结构；scale=0 一律非法；源缓冲只在旧白名单内。
**定位 →** 原 BitBlit 参数 144B，callback 在 `+0x80`，不是 Fill 的 `+0x28`。
先核几何、stride、范围和重叠，再看颜色和混合。
**解决 →** 逐步实现受限 Copy、RGBA4444、A8 字体着色、source-over、nearest。
未知模式仍拒绝，真正写像素后才按原格式完成。

当前软件显示桥的解释如下，它是显式模型而非所有 Sony 像素格式规范：

```text
像素：little-endian u16，数值 0xRGBA
R=(v>>12)&15，G=(v>>8)&15，B=(v>>4)&15，A=v&15
黑底合成的 8bit 通道 = (channel4 * 17 * A + 7) / 15（整数）
ramfb 输出内存字节为 B、G、R、0；配置格式为 XRGB8888。
```

**剩余 →** 硬件舍入、预乘约定和全部 GPE 格式尚未逐像素闭合。
显示桥与本模型逐像素一致，不能外推为与实体相机硬件一致。

## 小步骤 3：资源能打开，还要证明解码真正产出字节

**问题 →** 字体有了，背景和图标仍缺失，文字叠在一起。
**现象 →** 31 次真实 format7 LZ77 调用因 `/dev/ldec` 缺席失败。
**误判 →** 资源文件已打开就是“资源支持”；对失败解码补成功即可出图。
**定位 →** 沿原资源→解码请求→输出 buffer→位图锁/解锁追踪。
**解决 →** 用同格式 CPU Sony LZ77 解码，检查终止、回距、输入消费和精确输出尺寸。
九份资源与参考实现逐字节匹配；实际菜单 31/31 解码成功，图标与背景出现。
**剩余 →** 只覆盖已核资源路径，不代表 LDEC DMA 驱动或任意压缩格式已模拟。
字体来源及两个语言字体 pins 见[资产篇](boot-assets.md)，不能用宿主字体替代后声称原字体消费。

## 小步骤 4：第一张离屏图之后，还得让第二帧返回

**问题 →** 离屏菜单存在，第二次 drawFramebuffer 却不返回。
**现象 →** ready 信号量 `0x02886047` 已返回，实际等 ExternalOSDIF gate `0x02886044`。
**误判 →** 把两把 gate 混同，或者只发送完成 ACK 掩盖缺失消费者。
**定位 →** 核原 LIRO 1002 控制、1003/1005 输出与 6003/6005 完成的配对。
**解决 →** 显式 AP-only 接收端真正复制当前像素，完整提交读回后才通知完成。
1005 只可引用上一成功保留帧；它不能凭空成为新像素。
原双缓冲交换、第二帧返回和完成通知都有独立证据。
**剩余 →** LIRO/CP/面板完整硬件链仍未恢复，失败提交继续拒绝 ACK。

## 小步骤 5：把租期、元数据和像素绑成一份提交

**问题 →** 前后 descriptor 相同也不能保证复制期间像素不变。
**现象 →** 并发绘图、resize、teardown 都可能让采集读到混合帧。
**误判 →** gate 关闭就等于缓冲稳定；事后读显存即可代表当时画面。
**定位 →** 检查 FB 生命周期锁、Bitmap AddRef/ReadLock 和共享 raster 锁。
**解决 →** 锁内复制到私有 buffer，逆序释放，文件 I/O 和通知放在锁外。
输出 HOSDAP02 将头、metadata、像素绑定到同一 inode，并完整写入读回校验。

| 部分 | 字节数 | 作用 |
| --- | ---: | --- |
| header | 128 | 容器身份与校验 |
| metadata | 24930 | 同次描述与事务信息 |
| 像素 | 614400 | 640×480×2 |
| 全容器 | 639458 | 单份完整提交 |

**剩余 →** 事务 seq 增长可只是 metadata 更新；要另看 `pixel_source_seq`。
同一张图长得相同，也不能代替本次提交/租期的证据。

## 小步骤 6：证明这份像素到达唯一窗口

**问题 →** QEMU 有 GTK 后端，也不会自动消费 Sony 私有 OSD。
**现象 →** 旧构建只有 none/curses；打开图形窗仍看不到 AP 位图。
**误判 →** “能开窗口”就等于显示适配完成。
**定位 →** 历史 ramfb-viewer 校验容器，转 XRGB8888，经 fw_cfg DMA 配置 `etc/ramfb`。
**解决 →** AP 转换结果、QMP 截帧与实际 GTK 画布分别逐像素核对。
新版单机身 GTK 窗把 640×480 LCD 与控件合在一起，QEMU 使用 none 显示后端。
**剩余 →** 单窗整合是表现层，不能增加 CMOS、按键或拍摄的验收范围。

```bash
# 执行目录：$PKG；只读查当前软件转换和窗口接线
cd "$PKG"
rg -n 'static void convert|DRM_FORMAT_XRGB8888|putbe' runtime/analysis/ramfb-viewer.c
rg -n 'native_display|640|480' runtime/analysis/camera_ui.py
```

## 解决了什么，仍未解决什么

原资源、真实绘图、带租期提交和窗口消费组成了已验的 AP 软件显示链。
自然简中首设、HUD/MENU在本包已有后续限定验收，旧黑屏阶段不是最新功能结论。
取景区域仍黑；F12、PNG 和 HOSDAP02 都是界面快照，不是相机照片。
输出新黑帧时要看新事务与业务生命周期，不能冻结旧菜单伪装持续工作。

## 如果你在做别的机型

Sony GPE、UXC、LZ77 和 LIRO 消息配对需要重新核。
先区分“有没有画”“有没有提交”“有没有消费”，再做窗口美化。
可复用的是格式/字节序核验、真实解码、缓冲租期与逐层像素对照。
