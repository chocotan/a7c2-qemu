## 这次推进了什么

完整冻结批次已包含两项内容检查器修复：一项恢复串口粘连前缀中的完整传输记录，另一项要求 ADF 图连接修复真正关联请求、完整消息、回调及生命周期，而不是仅凭日志标签放行。v2 六例、v3 七例自有夹具均经实际插件 API 验证；它们执行的是自有测试程序，不能算原 Sony 拍摄。独立复核覆盖全部归档成员、full64 数据、命令、产物、源码和业务二进制；13 项外部资产与三份业务库保持不变，插件沿用已验构建。

首个完整批次有一个新增重复字段负例的预期写错，原失败保留。只纠正该测试对异常的预期后，新批次通过；重复 JSON key 的严格拒绝没有放宽。冻结快照之后的源码修补仍待集中验证，不包含在上述 PASS 内。

## 仍需解决的问题

最近原生运行 `run-64f9ieca` 已完成原启动与自然快门序列提交，原流程和严格退出保全通过；取消、调试器分离、所属 owner 退出和两把现存锁的独占核验均有记录。原正式 **capture FAIL / graph FAIL 永久保留**，卡上没有 JPEG/MP4。只读观察与原 Main 上下文绑定通过，但 M 比较值为 0、两处已知 writer 未观察到执行；这不能证明所有 M 写入均未发生，也没有证明实际分支执行、写入或返回。正常 producer、reader 与更长间接寻址仍未知。

新检查器对同一次运行的复核越过了原 seq3 覆盖问题：27 条实际 guest bridge 记录覆盖全部 36 个 broker 回复，序号差集为空。复核随后仍被两处阻塞：控制提交记录与精确内核尾注粘在同一行而被拒绝；研究工具的读取限制又拦住了 graph 所需的原模块 SHA/指令只读核对。因此结果仍是 INCOMPLETE，不能称为实际总线丢包，也不能跳过原模块验证或回填原失败。六个入口各进入一次，八个依赖入口未进入，原输入账本前后不变。

下一步先合并这两项有界修复，集中验证完整批次和同一次运行的内容关联。原固件拍摄的终点仍是：**原 AP 触发 → 实际虚拟 CMOS 帧 → 编码模型消费 → 原 MPR/Fsys 写虚拟 SD → 读回并独立解码**。只有整链实际通过才改变 `capture_verified`；录像还须验证自然停止、文件收尾和可播放的最终 MP4。目前没有完成时间承诺。
