# 大步骤 8：从提示反查状态，再做有效容量对照

这篇解决媒体提示、属性层与容量实验的证据陷阱，不宣称已找到“无空间”的完整根因或恢复录像。

变量见[索引](README.md)。本次未读卡镜像、未改状态、未运行容量实验。

## 小步骤 1：先锁定最终选择规则，而不是猜提示来源

**问题 →** 原REC显示“插槽2无卡”，修掉遗留强写后变成“存储卡无空间”。
**现象 →** 修后原最终selector多次选`0x223`，记录VA`0x5905988`、predicate`0x187f130`。
**误判 →** LCD一句话就证明物理槽、容量或某个上游状态必然正确。
**定位 →** 同一原调用配对entry/return，读最终记录、predicate和message list。
主消息`0x0200a1b4`，备用`0x0200a04a`，资源文本分别是插槽1无空间/无空间。
**解决 →** 证明了“本次原选择的是哪类提示”，不再把无卡与无空间混成一个问题。
该谓词本身没有做空间算术，应沿其真实读取字段追上游。
**剩余 →** 消息类别不证明整条挂载/可录制映射正确，host提交REC时间也不是原消费PC。

## 小步骤 2：先区分基值/复位源与当前值访问器

**问题 →** 原属性表看似能读出状态，实际选错列。
**现象 →** 旧日志将`0x5584c38`行`+08`读数叫实时值，102d/e是0/30。
**误判 →** 0/30说明整个启动从未更新，或者0必然代表未挂载/不可录。
**定位 →** 核原通用API：`0x28bb0ac`走`+08`，`0x28bb0c8`走`+20`。
再核ROM初始化、复位源和实际LDR，不能只把observer标签改名。

| 分发表键 | `+08`基值cell | `+20`值层cell | 已核角色 |
| --- | --- | --- | --- |
| `0x102d` | `0x7e83b28` | `0x7e83b10` | 两层是不同地址 |
| `0x102e` | `0x7e83b48` | `0x7e83b30` | 两层是不同地址 |

**解决 →** 旧`+08`保留为`_base08`，值层另采，每个事件标`media_observation_revision=2`。
修后原运行64对entry/return中，两层102d/e这次都为0/30，selector62次223/2次ffff。
这描述的是历史revision2样本。当前revision3改用中性的`dispatch_<key>_value20/base08`字段名，并明确所有目录名字绑定均未验证；地址与读取宽度保持不变。
**剩余 →** 新样本只证明本次时刻读数，不能追溯修补旧日志，也未证明枚举语义与写入历史。
`+10/+18`是setter，不能把基值、shadow、current合成同一单元。

## 小步骤 3：名字目录编号与分发表键单独证明

**问题 →** 相同编号在两张表里看起来对应同一参数。
**现象 →** 名字目录`0x1052`指向“建新文件夹剩余容量”，分发表同号却有`(-15,15,1)`校验。
**误判 →** 因名字有capacity，就把读数0写成“剩余容量=0”。
**定位 →** 反查该行setter的validator、转接ROM表和真实调用字符串。
已核运行转接来自`0x103c`，原字符串为`set_picture_profile_black_level`。
**解决 →** 将1052从媒体字段集合移除，改称`dispatch_1052_unresolved_value/base08`。
原“剩余容量为0”的说法撤回，地址读得准不等于名字绑定得对。
本行已证受PP黑电平路径转接、值域为-15..15；不是媒体容量统计。
**剩余 →** 名字目录与分发表全局同一性仍未证，真正容量消费者也仍未知。
这条限制适用于所有仅由目录派生的媒体PRM标签，不只1052。
102d/e等读数也只按键、访问器和原字节角色记账，不能借旧标签证明挂载/可录枚举。

## 小步骤 4：校验器和序列化导入不是实时生产者

**问题 →** 大函数读到相同属性ID，就被称为状态apply/发布者。
**现象 →** `0x2e2232c`读取snapshot+b60/b64，传102d/e到`0x28bbcc8`。
**误判 →** 把`0x56c4118`叫write-table，把379d字节当snapshot长度。
**定位 →** 核24B记录、函数指针与返回用途：这里是范围/枚举validator。
379d字节是按propertyID索引的状态表；mode导入缓冲stride为`0x2074`。
**解决 →** 两个已核序列化键`0x02cf0f05/0x02cf0b91`保留为设置键，不改叫CP消息ID。
初始化常量、恢复校验和序列化解析从实时生产者候选中分开。
**剩余 →** 真实setter调用栈、shadow→current提交与媒体消息writer仍需实际观察。
按偏移扫到store只是候选，不证明对象同一或唯一生产者。

## 小步骤 5：先让镜像合法，才能谈业务拒绝

**问题 →** 想以更大卡验证提示，但实验可能在启动前就失败。
**现象 →** 首轮1GiB FAT16，文件2097152扇区，默认63sectors/track使BPB仅2097144。
**误判 →** fsck0就是完全满足当前后端约束；输入拒绝就算大卡无效。
**定位 →** 同时记录mkfs返回、原512B BPB、文件大小、扇区大小、总扇区与fsck。
**解决 →** 格式化几何改为64heads/32sectors，保持后端严格全长检查。
断言前先保存构造证据；已有文件拒绝覆盖，失败输入保留。
**剩余 →** 此问题是工具默认几何与后端契约不符，不是原REC业务容量拒绝。

```bash
# 执行目录：自己的独立实验目录；IMG为已构造、已关闭的普通镜像
# 下面只读检查，不创建/修复镜像
fsck.fat -n "$IMG"
python3 - "$IMG" <<'PY'
import os, struct, sys
with open(sys.argv[1], 'rb') as f:
    b = f.read(512)
    size = os.fstat(f.fileno()).st_size
bps = struct.unpack_from('<H', b, 11)[0]
total = struct.unpack_from('<H', b, 19)[0] or struct.unpack_from('<I', b, 32)[0]
print('file_bytes=', size, 'bytes_per_sector=', bps, 'total_sectors=', total)
print('bpb_bytes=', bps * total, 'sectors_per_cluster=', b[13])
PY
```

该片段只显示几项BPB字段，不是完整FAT合法性验证器；它不替代fsck或后端前检。

## 小步骤 6：合法镜像之后，还要核 guest 的交付资源

**问题 →** host镜像有效，guest仍没到原应用。
**现象 →** 1GiB输入加原cpio解包约1587381KiB时OOM；没有shell/appFw/REC。
**误判 →** QEMU `-m24GiB`就给kernel24GiB；只检查initrd地址不重叠即可。
**定位 →** 核DTB RAM长度`0x140000000`即5GiB，Sony预留后实际可用1190024KiB。
**解决 →** 仅对已证空白零尾输入，改用metadata prefix+零洞的无损表示。
guest重建普通文件后，启动原bootin前完整OpenSSL SHA必须等于完整源输入。
**剩余 →** 该方案没扩大RAM，也不能交付任意非零尾大卡，未作为本包任意大卡支持发布。

## 小步骤 7：连精简工具的参数也先自证

**问题 →** 稀疏重建脚本用了BusyBox没有的参数。
**现象 →** 原`dd`不支持`conv=notrunc`，set-e提前退出，bootin被SHA门挡住。
**误判 →** GUI exporter失败代表原容量条件无效。
**定位 →** 查原console及App/Frame/RM/FsysMount计数，全为0，定位到构造脚本。
**解决 →** 历史使用同一原BusyBox二进制自证不带conv的seek行为保留prefix。
随后仍要求guest全镜像SHA匹配才进原程序，不降低启动门槛。
**剩余 →** 工具行为要按目标构建核，不能从宿主GNU dd手册推断。

## 小步骤 8：有效对照完成后，只下案例内的结论

**问题 →** 即使大卡仍拒绝，也容易宣布“容量全部无关”。
**现象 →** 最终1GiB原RM接受1073741824B，Fsys空闲64917/65518个16KiB簇，约1014.33MiB。
**误判 →** 更大输入一定修复；或一个失败案例能排除所有容量/格式/配置条件。
**定位 →** 核实际guest输入SHA、原GetFree完整8word、原REC规则与LCD。
**解决 →** 有效案例仍显示无空间，64对selector中62次223/2次ffff。
256×4MiB导出、整卡SHA、fsck0、Flush/owner和CPU恢复另行通过。
**剩余 →** 只说明这组更大合法FAT16输入不足以解除拒绝。
交付表示和簇大小也与128MiB不同，不能写成严格单因素容量因果证明。

## 解决了什么，仍未解决什么

建立了规则、读值层和有效输入案例；撤回了“挂载/剩余状态必为零”“唯一根因是逻辑槽”等旧解释。
原Fsys实有空闲不代表已排除上层最小容量/格式/配置门槛。
没有写remaining/recordable/ready、选槽或清错来消提示，capture仍false。

## 如果你在做别的机型

Sony属性表、名字目录、规则索引和BK4键要重新定角色，不能按同号强绑。
可复用的是先校观测层、证明真实writer、让输入合法，再把失败定位到构造/传输/消费/业务。
一次改变一个变量；无法避免混杂时，主动收窄结论而不是补根因故事。
