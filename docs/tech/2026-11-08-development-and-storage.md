# 开发面板、内部单盘与启动内存修复

本轮在独立产品 `final/a7c2-qemu` 中维护运行代码。外部输入仍为用户自己的 2.01 ALLLANG BODYDATA 和固定 QEMU 11.1.2 源码；不依赖研究仓库、系统 dump 或历史实验目录。完整 BODYDATA 更新、拍摄写卡按用户要求暂缓，均不计为通过。

**已完成文件测试、同盘重启保留、原版恢复，以及默认入口兼容验收。** 原版恢复的首次关闭超时保留为失败；从已验证的第二轮分区快照创建独立候选后，恢复与正常保存补验通过，未改写成连续三次无失败。详见[原 AP 文件周期收据](../../validation/persistent-file-cycle-20261108.json)、[集中验收](../../validation/product-integration-20261108.json)和[默认入口收据](../../validation/default-after-integration-20261108.json)。

## 产品行为

GTK“固件开发”提供文件测试、启动测试和更新三个区域。文件选择和内部磁盘开关只允许在 VM 保存退出后操作；开发动作与按键、关闭、重置、网络及 SD 动作共享互斥状态。

测试文件先复制到独立目录，核原文件未在复制中变化，再读回完整 SHA。运行后复用同一串口所有权通道，核原 guest 的 Uid/Gid 各四零字段、文件 SHA 和长度。暂存成功与 guest 已实际消费分别显示。选择原版显式绕过默认 overwrite；重复选择原版仍保留同一恢复目标。

内部盘为显式默认关闭选项，可通过窗口或 `./start.sh --persistent-storage` 启用。持久模式只接受包内已有 `/usr` 普通文件作为测试目标，以便恢复原版。写前保全原值，写后同步和完整 SHA 读回；同次选择重启不重复覆盖。原版选择恢复包内对应文件。

“关闭后重新启动”使用同一控制器的正常保存、退出和重新启动，不表示 RAM 保留热恢复。完整原 init/pivot 冷链与 WBI 热恢复仍未接齐，见[官方启动流程复核](2026-11-08-boot-review.md)。

## 独立构建与单盘

`source/persistent-flash/` 包含普通文件后端、QEMU 设备、自有 guest 块驱动和406个必要的 Sony 公开 Linux 4.9.337 依赖头，约2.5MiB。原版权、GPL全文、逐文件身份及相对构建命令一并保留；无需完整内核树。标准 AArch64 GCC/binutils 和 pyelftools 可重建模块，核 AArch64 ET_REL、原 vermagic、768B/64B 对齐模块布局及39个原内核符号（含 bdget_disk/bdput/freeze_bdev/thaw_bdev）。

初版曾核对除 build-id 外 ALLOC 区段与103项语义重定位等价；后续按原 brd 实现补写前/读后 `flush_dcache_page`，因此不再把新模块称为初版字节一致。构建、短原内核块组件和原 AP 集成分别记账。

产品在固定三段 QEMU 补丁、DMA/PCI stage 后加入默认关闭的持久设备。必须显式提供 profile 和父进程持有的普通文件 FD/dev/ino，拒绝物理块设备。USB xHCI 保持 `0x0b000000..0x0b004000`，持久设备使用 `0x0b010000`。同一 OFD 排他租约贯穿控制器、launcher、sandbox 和 QEMU，全部 owner/后裔退出后才释放。

factory 仅从产品校验过的官方包缓存生成。官方有提供的镜像保留原内容；缺失卷明确创建虚拟默认卷，使用公开 PP，未引入设备私有数据。原 ext2 扩容前后全树内容、权限、所有权、ACL及链接一致，fsck 通过。容器用户区 1,954,545,664B，加两个各4MiB boot 区，总计 1,962,934,272B；19片初始写入全部读回。已存在实例复用原盘，不在每次启动重铺 Backup/settings。

## 故障原因与修复证据

| 问题 | 原证据及结论 | 修复 |
|---|---|---|
| 继承 preload 的辅助程序主动加载 AP 密码库 | 原 helper/bootin 在 loader 初始化故障；仅限制进程仍不足 | 构造器只解析原函数；真实 bootin/im 请求 appFw 时才装载依赖，核实际 exe 路径 |
| 原 init 环境遗漏 | 原 init 导出 `WBSHD=/tmp_wbshd/shared.XXXXXX` 和 allocator 变量；原 loader 日志却曾读取 `/tmp/shared.*` | 补齐原环境及 WBSHD tmpfs；原六关键 ELF 全 SHA 门保留，旧 loader 故障随后未再现 |
| 小临时卷被失败遗留占满 | 12MiB p10 可见文件约3.8MiB，另有518孤链/8,486,912B | 原失败盘保全，仅独立候选回收；普通命名文件树及其它18片不变，实际核空闲簇。初次 `fsck -a` 救成12个恢复文件而未释放空间的错误判据/失败也保留 |
| 重启后模拟服务排他拒绝 | 持久 `/tmp/rm-file.claim` 导致原排他检查拒绝，SD flush 无回复；OSD同类 | 在新 guest、独占磁盘租约、AP启动前只清本模拟器的 claim、IPC 请求、ready/快照状态；不清配置或全部临时卷 |
| 只读 `/usr` 遮蔽运行适配 | 原日志明确 `cp startBTCore.sh: Read-only file system`，随后执行原硬件脚本 | 持久模式对已验虚拟 HCI 脚本用只读 bind，核实际文件摘要；原 RAM 路线保留已有复制行为 |
| 固定20秒启动等待抢先判失败 | 主机 I/O 压力时，日期 marker 检查已开始，guest 仍在处理前面的挂载命令 | 先通过原串口完成边界确认 setup 全部消费，再开始原 AP 等待；timeout 仍保留失败 |
| initrd 与 Sony 图像保留区重叠 | 实际 DT 的655.6MiB initrd 位于 `0x440000000..0x468f99e90`，完全落在原 `0x430400000..0x500000000` 保留区；原内核 `free_initrd_mem` 直接释放整段，失败 task 物理地址亦落在此区 | 实际 loader 与 DT 同移 `0x504000000`；显式6GiB虚拟 RAM，载荷末端不得超过 `0x580000000`。原内核、图像保留区和内核异常检查均不修改 |
| 内部卷缺关闭收尾 | SD/设置快照成功及 QMP0 并不表示内部 FAT 一致；旧第二次启动曾出现 setting 坏簇/SLAB异常 | 只读重挂和正常卸载因原内核文件引用仍会被拒绝，失败保留。最终由自有块驱动调用原 freeze_bdev，同步冻结全部19个分区并保存引用；失败调用原 thaw_bdev 逆序恢复。原 sysfs 实际状态/数量必须为1/19，停止后独立核文件系统结构。禁止强制重挂/强制卸载 |

原 kikilog ELF 的正常退出链明确调用 `filp_close`；它持有的文件不会出现在用户进程 `/proc/*/fd`。实际正常 rmmod 仍返回资源不可用，因此该方案未被当作通过。最终冻结接口保留原引用并让内核完成写入隔离；不退出原服务或卸载原模块。生产C函数的正常、幂等、中途失败回滚、解冻失败时保留引用均有host执行测试。原内核实际冻结读回1/19、失败恢复0/0已验证；最初sysfs额外空行导致严格解析拒绝的原失败也保留。

冻结快照仍可带FAT的mounted-dirty标志，因此独立 `fsck.fat -n` 原返回码及输出全部保留；只有内容严格仅提示dirty标志时，才单独记录结构一致，不写成fsck0或正常卸载。任何坏簇、孤链、长度修复、未知输出仍失败；ext2继续要求e2fsck0。

早期收尾脚本曾在 PID 1 shell 中执行 `exit`，触发原内核 panic。该错误及原结果保留；收尾现在在子 shell 内执行并豁免 PID 1，不将失败回填为成功。原 monitor 只读诊断使用 reg/call，以及同页最多128B的受限采样，不发送 exit 或内存写命令。

## 实际验证边界

- 磁盘清理：644个可重建验证文件路径核对，640重复路径共享；可用空间增加 442,088,669,184B（约411.73GiB），原路径、字节和失败记录保留。
- 正式集中验收使用两个工作线程、八组检查。首轮 host/source/GTK/附加组件/模块/依赖/旧脚本同步通过；公共模型原执行14,571项后因主机 I/O阻塞正常中断，279失败与原JUnit保留。共享 AST/UI/进程夹具、新源码合同与 Unix socket 过长问题集中修复；两个线程只恢复3,836个失败/未执行节点，未重复旧通过项。
- 恢复检查剩下5项：当前源码合同和 mock 关闭重试修后通过，另外3项依赖原库与 QEMU-user 的集成明确为 skip，不放宽公共 host 禁止执行 VM 的守卫，也不视为成片通过。
- 原 RAM 路线已实际核41B文件的 guest SHA/长度/四零权限、原 LCD 和正常保存退出，收据见 `validation/firmware-file-native-20261108.json`。短原内核块组件实际大/小块写读、四份 guest SHA、主机整盘和正常 QMP 退出见 `validation/persistent-flash-native-20261108.json`。
- 修正后的单盘首启动已核原 AP、文件、LCD、真 SD 保存、实际安全 initrd 地址、正常退出和五个卷 fsck0。第二次启动已越过此前内核栈异常，重启文件读回通过；最终写入41B、重启后41B保留、恢复52B原版的三个阶段都完成原AP/guest读回、LCD、真SD保存、19卷冻结、QMP0/无VM信号和租约释放；每阶段五个停止卷均结构一致，FAT原rc1只含dirty标志，ext2 rc0。首次恢复轮关闭时串口请求超时并留下192KiB孤链，原盘不改；恢复补验使用前一已验证快照的独立候选，通过后另记结果，不声称连续三轮无失败。
- 首轮干净关闭的 `/usr` 1,157条全树比对只有明确测试脚本一项差异，其余文件内容、权限、所有权、ACL和链接均与官方 factory 相同。
- 最终正式host为376通过/39跳过/95子测试通过；冻结状态机、真实DT边界、输入合同及runner补集201通过。公共模型按原/恢复/最后补验JUnit对相同节点取最新结果，为17,841通过/287跳过/0未解决失败，不与重叠子集重复相加；新增3个公开组件测试已接入249组正式入口，额外31项通过，清单计数回归另复验通过。
- 本轮直接默认 `./start.sh` 再次完成9步原首设、拍摄HUD、原菜单进入与返回、正常SD保存和QMP0退出，原用户配置未变。并行资产锁prelaunch拒绝、旧验收器2秒读连续帧竞争均保留；最终调用者未传HCI或持久盘环境变量。

## 保留的限制

完整原 bootloader/init/pivot 冷启动、RAM热恢复、USB宿主枚举和 jiritsu 认证 root 尚未通过。USB14槽真实消费仍有未知项，当前宿主 vhci 条件也不满足，不通过空 ACK 或假 ready 代替。严格全部按键样本小于100ms尚未通过；原低延迟收据的中位97.3ms、最大121.1ms保持原结论。

完整 BODYDATA 更新与拍摄写卡保持 deferred。本轮没有执行更新脚本、拍照或录像，没有连接真实相机/真实SD。原固件、失败盘、私有设置和原始运行输出均不随源码公开。
