# 大步骤 2：先校准地址，再做只读观测

这篇解决“地址看起来正确、实际读错对象”和探针清理问题，不提供通过调试器改业务状态的捷径。

目录变量见[索引](README.md)。本次没有连接任何调试端点。

## 小步骤 1：给每个地址标明坐标系

**问题 →** 同一个十六进制数可能是 fileoff、ELF VA、分析器地址或运行地址。
**现象 →** 曾误判 appFw 未建屏、属性没有更新，或把字符串桩当函数。
**误判 →** 直接从反编译函数名复制地址，或认为整个 ELF 的 VA 都等于 fileoff。
**定位 →** 先固定文件 SHA，再读取程序头；逐段换算，不能写一个全文件常量。

```bash
# 执行目录：$PKG；仅对已导入的自有普通 ELF 文件只读查阅
cd "$PKG"
readelf -lW runtime/analysis/menu-root/usr/lib/appFw.so
sha256sum runtime/analysis/menu-root/usr/lib/appFw.so
```

文件支持范围内的标准换算是：

```text
若 p_vaddr <= VA < p_vaddr + p_filesz：
    fileoff = p_offset + (VA - p_vaddr)
运行地址 = 已核装载偏移 + ELF VA
仅在 p_memsz 内、超出 p_filesz 的区域没有对应文件字节。
```

**解决 →** appFw 第二 PT_LOAD 为 `vaddr=0x51b7718, off=0x51a7718`。
这段满足 `VA=fileoff+0x10000`，属性表 `0x5584c38` 必须按此映射读取。
旧测试和被测字典曾共用错误偏移而“互证通过”；后来改成独立解析 ELF 段表。
**剩余 →** 此偏移只描述已核原件的该段，不描述所有库或新版本。

## 小步骤 2：从反编译器地址回到原字节

**问题 →** Ghidra、Kuna 和 CP 的地址命名方式不同。
**现象 →** `FUN_0313d400` 与实际 ELF VA `0x303d400` 相差 `0x100000`。
**误判 →** 把分析器 image base 偏移与 ELF 第二段偏移加到一起。
**定位 →** 看语料 manifest、归一化 `// addr` 和原件指令，不只看函数名。
**解决 →** AP 语料索引已经归一为 ELF VA，FUN/DAT 名字常仍保留分析器偏移。
例如 `FUN_0313d400` 需要回到 VA `0x303d400`，再按所属 PT_LOAD 查文件。
**剩余 →** 语料不是原厂可编译源码；间接调用、缺参数和函数边界还需原字节。

## 小步骤 3：CP 混合 ARM/Thumb 时重新核指令边界

**问题 →** CP 镜像含 ARM 启动码、Thumb、文本和数据。
**现象 →** 全库线性解码会产生假函数；数字加猜定基址偶然落到字符串。
**误判 →** 把 Gamma 曲线样点当字符串偏移表，把防尘 barrier 当成像启动屏障。
**定位 →** 本镜像使用 `CPVA=raw+0x108000`；先确认代码模式和消费者。
Thumb 函数指针 bit0 与实际指令地址分开处理，Kuna 合成 VA 也单独记。

```text
历史已核 ADR16：目标 = Align(指令地址 + 4, 4) + imm8 * 4
CPVA 0x3642d0 / raw 0x25c2d0：03 a1
目标为 0x3642e0；操作数显示的 #0xc 是相对量。
```

**解决 →** 消费者证实旧数组是 Gamma 曲线，真实字符串由 ADR 引用。
barrier 已核局部只有设置/一致性校验，不能据名字认作首帧等待。
**剩余 →** 这里没有证明传感器启动或 CP 完整运行。

## 小步骤 4：先证明停点读到的是本次活对象

**问题 →** 指针值相同不代表对象还是同一实例。
**现象 →** 队列调查曾漏合法分支，又在后续同址复用对象上继续关联。
**误判 →** 没命中一个中间 PC 就说 manager 阻塞；free/计数清零就说业务完成。
**定位 →** 同时绑定 run、原 ELF 身份、ASLR 基址、caller、线程和原调用帧。
在构造后关联对象，在析构或原 owner 释放时结束关联。
**解决 →** 请求队列观察改到两支共经的原指令，硬件 run/dtor guard 约束生命周期。
只在原 owner 仍持有向量/消息时读取；不事后解引用已释放 buffer。
**剩余 →** 硬断暂停 CPU 会改变时序，定位结果还需无此调试的独立业务复验。

## 小步骤 5：用写观察找作者，不替作者写值

**问题 →** 运行时异常值未必来自原固件。
**现象 →** 照片媒体字段 `appFw+0x7e6e7f0` 曾从 0 变成 1。
**误判 →** 把 1 解释成原默认配置，继续调整录像选槽或增加卡槽。
**定位 →** 先在原初始化入口读 baseline，再设置 4B 硬件写观察，记录原 PC/LR。
历史现场 PC 位于自研 observer，而非 appFw；核选用 initramfs 的库 SHA 和 store。
**解决 →** 定位到 `plane_config_send` 遗留 `KEY_GATE_OVERRIDE`，移除全部七项业务裸写。
后续实际原输入/HUD/MENU仍通过限定验收，REC 提示变化另行记录。
**剩余 →** 删除错误强写没有恢复成像；禁止通过断点改寄存器、改内存或调用 setter“验证”。

## 小步骤 6：观测结束后独立确认 CPU 恢复

**问题 →** 调试器退出不保证 guest 已继续执行。
**现象 →** 保存/teardown 可能在 CPU 仍暂停时开始，进一步掩盖原故障。
**误判 →** detach 输出成功就等同恢复；把 QMP CPU 状态与 Fsys owner STOP 混为一谈。
**定位 →** 本项目用独立私有 QMP 通道查 `query-status`，随后另做串口事务。
**解决 →** 删除自己的断点、detach、核 CPU 状态；必要的受控恢复后再次核 running。
CPU 恢复确认先于快照、存储导出和 GUI teardown。
不能确认时保留本次 VM/租约/控制目录，错误非零，不启动下一实例。
**剩余 →** 正常清理轮不能冒充所有异常组合已验；更不能强杀持卡进程来制造“已退出”。

## 小步骤 7：把“未命中”写成有界结论

**问题 →** 日志窗口、限流、采样上限和旧库都会制造阴性。
**现象 →** 前 64KiB 日志漏掉注册；源代码有内容 trace，实际库却未重建。
**误判 →** 没日志就说函数不存在、没有 Read，或原件没有生产者。
**定位 →** 保存完整 console、探针 source/ELF/cpio 身份、启用标记及 entry/return 配对数。
**解决 →** 区分墙钟截止、事件上限、读取错误和真正观察期内未命中。
入口 ready 只表示探针已布置，不能称相机 ready。
**剩余 →** 直接 xref=0 不排除虚表/间接调用，单偏移 store 扫描不证明唯一 writer。

## 解决了什么，仍未解决什么

地址校准、观察者自证、对象生命周期和独立恢复构成了可复用的调试流程。
这些流程得到的是定位证据；功能是否恢复仍要在对应大步骤单独验收。
本页不给裸 `target remote`/`set` 脚本，避免绕过实例身份和保存保护。

## 如果你在做别的机型

`+0x10000`、`+0x100000`、`+0x108000` 分属不同坐标系，都要重新核。
可复用的是原件身份→段映射→原指令→现场对象→独立清理的证据顺序。
硬件断点与被动 trace 是定位手段；状态修改是另一个实验，不能混写成只读观察。
